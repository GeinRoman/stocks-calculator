# Сборка и развёртывание релиза

[English](release.en.md)

Инструкция собирает и запускает Go-сервер, PostgreSQL, миграции и SvelteKit-интерфейс на локальной машине через Docker Compose. Релиз изолирован от разработки: проект Compose называется `stocks-calculator-release`, база хранится в отдельном постоянном томе. Данные разработки **не импортируются** автоматически.

Шлюз релиза по умолчанию слушает `127.0.0.1:8080`. Для доступа с других устройств настройте существующий HTTPS reverse proxy на том же хосте. Шлюз отдаёт интерфейс и направляет `/api/` на backend, удаляя префикс. База и backend напрямую наружу не публикуются.

## Требования

- Docker Engine с плагином Compose в Linux либо Docker Desktop с Compose в Windows.
- Linux: POSIX shell. Windows: PowerShell и запущенный Docker Desktop в режиме Linux-контейнеров.
- Исходный код или каталог релиза с frontend, backend, миграциями и Dockerfile.
- Доступ к интернету для базовых образов, Go-модулей, npm-пакетов и MOEX. Внешний прокси должен иметь действующий HTTPS-сертификат для публичного имени.

Команды выполняются из корня проекта. Релизные образы собираются из исходников; установка Go и Node.js на хосте не требуется.

## Закрытая конфигурация

Перед запуском создайте **оба** файла в корне проекта. Они исключены из Git и контекста сборки Docker. Не добавляйте их в репозиторий, отчёты об ошибках и публичные сообщения.

### `release.env`

Создайте файл со своими значениями:

```dotenv
DATABASE_USER=stocksapp
DATABASE_PASSWORD=ЗАМЕНИТЕ_СЛУЧАЙНЫМ_HEX_ПАРОЛЕМ
RELEASE_PORT=8080
```

- `DATABASE_USER` и `DATABASE_PASSWORD` используются для создания релизной базы и подключения к ней. Выберите уникальный надёжный пароль. Текущие строки подключения backend и миграций вставляют эти значения без URL-кодирования: используйте имя из латинских букв и цифр и **шестнадцатеричный пароль**, без знаков пунктуации, пробелов, `$` и специальных символов URI.
- `RELEASE_PORT` — порт шлюза на **loopback-интерфейсе** хоста; выберите свободный порт и укажите его во внешнем HTTPS-прокси. Это не порт backend.
- Переменные, уже экспортированные в оболочке, имеют приоритет над `release.env` в Docker Compose. Избегайте конфликтующих `DATABASE_USER`, `DATABASE_PASSWORD` и `RELEASE_PORT`.
- PostgreSQL использует эти данные только при первом создании тома. Последующее изменение файла **не меняет** пароль в базе; смену учётных данных необходимо согласованно выполнить в PostgreSQL и приложении.

### `release.config.yaml`

Создайте отдельный файл конфигурации backend:

```yaml
max_connections: 100
jwt_key: "ЗАМЕНИТЕ_ДРУГИМ_СЛУЧАЙНЫМ_HEX_КЛЮЧОМ"
jwt_expiration_time_min: 10
```

- `jwt_key` подписывает и проверяет токены аутентификации. Создайте уникальный непредсказуемый секрет не менее чем из 32 случайных байт в шестнадцатеричном виде. Скрипты требуют указать hex-значение в отдельной строке YAML; допускаются двойные кавычки. Не используйте ключ разработки из `config.yaml` и не повторяйте пароль базы. Зная ключ, можно подделывать токены.
- Сохраняйте ключ при обновлениях и перезапусках. Его смена делает ранее выданные токены недействительными, и пользователям придётся войти заново. При компрометации смените ключ осознанно и защитите содержащие его резервные копии.
- `jwt_expiration_time_min` задаёт срок действия access-токена в минутах. `max_connections` ограничивает число подключений backend к базе; задайте положительное значение с учётом возможностей PostgreSQL.
- Backend читает файл при запуске. После изменения перезапустите сервис, как описано ниже. Рабочий ключ не включается в образ.
- Ограничьте доступ к файлам администратором развёртывания; например, в Linux: `chmod 600 release.env release.config.yaml`. Убедитесь, что Docker может прочитать монтируемый файл. Контейнер backend работает от root, чтобы читать файл владельца хоста с такими правами.

Пароль и ключ следует сгенерировать **отдельно**. Например, дважды выполните `openssl rand -hex 32` в Linux либо дважды выполните в PowerShell:

```powershell
$bytes = New-Object byte[] 32
[System.Security.Cryptography.RandomNumberGenerator]::Create().GetBytes($bytes)
-join ($bytes | ForEach-Object { $_.ToString('x2') })
```

Вставьте результаты в соответствующие файлы: без кавычек в `release.env` и внутри YAML-кавычек для `jwt_key`. Вывод терминала, историю и резервные копии следует считать конфиденциальными.

## Сборка и запуск

Linux:

```sh
./deploy.sh
```

Windows PowerShell:

```powershell
.\deploy.ps1
```

Скрипт собирает релизные образы, запускает PostgreSQL, применяет существующие up-миграции и затем запускает backend, frontend и шлюз. При ошибке Compose возвращается ненулевой статус. Скрипт не удаляет данные базы.

Для локальной проверки откройте `http://127.0.0.1:8080` (или настроенный порт). Это **не HTTPS**; не используйте его для удалённого доступа или настоящих учётных данных. Направьте существующий HTTPS reverse proxy на `http://127.0.0.1:8080`, сохраняя путь и host и передавая исходную схему. Настройте на внешнем прокси ограничение загрузки не менее 33 МиБ для импорта снимков и проверьте передачу сайта и `/api/` на шлюз. TLS завершается на внешнем прокси; не открывайте loopback HTTP-порт наружу. Refresh-токены хранятся в local storage браузера, поэтому важны HTTPS и контроль доступа.

Например, для установленного на хосте Nginx можно использовать следующий блок после замены имени, путей к сертификатам и при необходимости порта. Сертификаты нужно получать и продлевать отдельно; проверьте конфигурацию и перезагрузите Nginx обычным для хоста способом:

```nginx
server {
    listen 443 ssl;
    server_name portfolio.example.com;
    ssl_certificate /path/to/fullchain.pem;
    ssl_certificate_key /path/to/private-key.pem;
    client_max_body_size 33m;

    location / {
        proxy_pass http://127.0.0.1:8080;
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    }
}
```

## Эксплуатация

После сборки образов скриптом развёртывания запустить релиз без пересборки можно так:

```sh
./start.sh
```

```powershell
.\start.ps1
```

Чтобы при необходимости запустить стек и затем перезапустить backend, frontend и шлюз, используйте `./start.sh restart` в Linux или `.\start.ps1 restart` в Windows. PostgreSQL продолжает работать; скрипты не удаляют тома. В обоих режимах перед запуском сервисов проверяется готовность базы и применение up-миграций. Изменённые исходники эти скрипты не собирают: для обновления снова запустите скрипт развёртывания.

Во всех командах используйте одно имя проекта и env-файл:

```sh
docker compose --env-file release.env -p stocks-calculator-release -f compose.release.yaml ps
docker compose --env-file release.env -p stocks-calculator-release -f compose.release.yaml logs --tail=100
```

После обновления исходников сделайте резервную копию и снова запустите скрипт развёртывания. Миграции применяются до запуска backend; при последующей ошибке они автоматически не откатываются. После изменения `release.config.yaml` перезапустите backend:

```sh
docker compose --env-file release.env -p stocks-calculator-release -f compose.release.yaml restart server
```

Остановка без удаления данных:

```sh
docker compose --env-file release.env -p stocks-calculator-release -f compose.release.yaml down
```

Не добавляйте `-v`, если не намерены удалить релизную базу. Перед обновлениями сохраняйте PostgreSQL проверенным способом резервного копирования и храните дамп и закрытую конфигурацию в защищённом месте. На вкладке профиля также можно экспортировать JSON-снимок отдельного аккаунта; он не заменяет полную резервную копию базы. Проверяйте восстановление на отдельном временном экземпляре, а не в рабочей базе без плана восстановления.

Если запуск не удался, проверьте `ps`, журналы сервисов, учётные данные базы, файл конфигурации и доступность порта. При ошибке миграции backend не запустится; перед исправлением состояния миграций изучите причину и сделайте копию базы. Проблемы сети или MOEX могут влиять на запросы рыночных данных. Не публикуйте пароли и токены в журналах и обращениях за поддержкой.
